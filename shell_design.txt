(1) Describe how your implementation ensures that concurrent
    commands are executed concurrently instead of one after 
    another.
In run_command_line (lines 461-507), each external command is forked through 
the method fork_one_external (lines 341-383), which forks and execvs the child 
but returns immediately without calling waitpid. All commands on the line are
forked in this loop first, meaning all child processes exist and are running 
concurrently. Only after every command has been forked does a second loop call 
waitpid on each pid, making sure the shell doesn't move on until all of them finish. 

(2) One potential strategy for redirecting output is to run 
    the following code:

  ```
  FILE* output = fopen(filename, "w");
  stdout = output;
  stderr = output;
  ```

  This causes everything that would normally be written to 
  `stdout` to instead be written to the file described by 
  filename. Unfortunately, this strategy does not work for 
  output redirection in utcsh. More generally, it does not
  work any time fork-and-exec is used and we want to 
  redirect the output of the child process.

  Explain why this technique does not work when used in 
  conjunction with fork-and-exec, and why the dup2() 
  technique does not suffer the same issue.

  In utcsh.c in exec_external_cmd(), in lines 326-333.
When we call fork and exec, we are creating child processes and wiping out the
current program's memory, however stdout and stderr are just variables inside
that current program, so when exec is called those variables are not 
transferred to the child process. The dup2() is a system call which the child
process gets a copy of, so it is able to point to the same open file that was
originally described within the parent process.
